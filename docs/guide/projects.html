Projects, files and history

A project is a set of files: a main document, the files it includes, its images and bibliographies. On the desktop it is a folder on your disk; in the browser, it is kept in the browser. Either way it has a history of its versions.

Projects

Opening
File › Open Project Folder… (Ctrl+O) opens a folder Desktop only; recent projects are under File › Open Recent, in the project menu beside the project's name, and on the start page. On the desktop you can also give a folder when starting TeXCraft: texcraft path/to/project. A file larger than 64 MB (a reference PDF, a dataset) does not stop the project opening: it is not loaded, stays in the folder untouched, and is not part of the build; the status line names it with its size.
Saving
A project that has a place (a folder, or a name in the browser) saves itself: about a second and a half after you stop typing, when the window loses the keyboard focus, and before the project closes, its changed files are written to its folder, or in the browser to the browser's storage. Beside the project's name the top bar says All changes saved or Saving…; when a write fails it says Not saved, the status line says why, and leaving the project asks first. File › Save (Ctrl+S) saves at once and makes a version (in the browser the entry reads Keep in This Browser). A new project has no place yet: its first save asks where, and until then the dot after its name means unsaved changes and closing asks. File › Save Project As… (Ctrl+Shift+S) copies the project to another folder, or in the browser saves it under another name. To save only when you say so, turn off Save automatically in Settings › Editor.
When saving fails
The question asked before the project closes then says so: on the desktop The last changes to … could not be saved, with Try Again, Don't Save or Cancel; in the browser The last changes to … could not be kept in this browser, with Try Again, Don't Keep or Cancel. Nothing leaves your computer: for a project opened from GitLab or GitHub, the question also offers Commit to GitLab…, which keeps the changes first and then opens the commit dialog.
Renaming
Click the project's name in the top bar and type. On the desktop this renames the project's folder; an untitled project is saved under the name you type.
The main document
The file that is built, marked in the file tree. Choose another .tex file with Set as Main Document in its menu.

Files and folders

The Project Files section of the side panel lists the project's files and folders. Click a file to open it in a tab; images are shown in the editor's place. The tab's × or Ctrl+W (Close File in All Commands) closes the tab.

  • File › Add to Project › New File… and New Folder… ask for a path in the project, such as chapters/intro.tex.
  • A file's menu (right-click, or the menu key when it has the keyboard) has Rename…, Move to…, Delete… and Set as Main Document; an image's has Insert in Document.
  • Drag a file onto a folder to move it there.

Importing a project

File › Import a Project… (Ctrl+Shift+O, Cmd+Shift+O on a Mac), or Import… on the start page, brings in a project from wherever it is. Choose where it comes from:

GitLab, GitHub
Sign in (or use a personal access token), then type part of the project's name to pick it from your projects, or paste its address; its branch is chosen for you. See GitLab and GitHub.
Overleaf Desktop only
Paste the project's git clone address (a whole git clone … line is fine) and a git token made in your Overleaf account settings; your password does not work there. See Importing from Overleaf.
GitLab Server
A project on your organisation's GitLab, once the server is added (the card adds it the first time).
Git Address Desktop only
Any repository over HTTPS. TeXCraft checks the address as you type: a public repository shows its branches; one that needs signing in asks for a user name and a password or token. An SSH address (git@host:…) is offered in its HTTPS form.
Folder
On the desktop, the same as Open Folder…: the project opens where it is. In the browser, the folder's files are copied into a new project in the browser.
Zip File
On the desktop, the zip is unzipped into a new folder and opens there; in the browser it becomes a project kept in the browser. A zip whose files are all in one folder is unwrapped.

On the desktop, a project from GitLab, GitHub, Overleaf or a git address is a real git clone: Into says where, in your Documents folder by default, named after the project; Change… picks another place, which new projects then use. A folder that is there already and not empty is flagged, with a free name to use instead. The clone has the whole history, up to 200 MB, its remote set and its branch following it, so Sync works at once. When you press Import, the dialog closes and a card for the project appears at once at the head of the start page's recent projects, with a spinner, Importing… and the step it is at (Receiving the history…, Writing the files…), said aloud by a screen reader at each step. Cancel on the card stops it and removes the folder it made. When it is done the project opens; if you opened another project meanwhile, it is not replaced: the imported one joins the recent projects instead. If the import fails, the card says why in words, with Try Again (the dialog's page as you left it) and Dismiss. In the browser, a GitLab or GitHub import shows the same card while its files come. With a token, Remember on this computer (ticked at first) keeps it in your system's keychain, so Sync, Push, Pull and the next import from that server need none, after a restart too; Settings › Accounts lists the tokens kept, with Replace… and Forget.

In the browser, Overleaf and git addresses are shown but cannot be used: their servers do not answer web pages. Their card says so, with Get the Desktop App and Import a Zip File… (download the project as a zip on its site first).

Adding files, folders and zip files

File › Add to Project › Add Files… copies files into the project. You can also drop files on the window:

  • Files are added at the project's top level.
  • A folder is added with its files and its folders.
  • A zip file asks first: Unzip into the Project, Add the Zip as a File or Cancel. File › Add to Project › Import a Zip File… unzips without asking. When everything in a zip is inside one folder, that folder is left off the paths.

When files of the same name are there already, one question covers the whole drop: Replace, Keep Both (the new one gets another name, such as figure-2.png) or Skip.

Some things are always left out, and the status line says what and why: hidden files and folders (such as .git), the build's leftovers (.aux, .log, .synctex.gz, .toc…), links that point out of the folder, and names in a zip that would land outside the project. An import holds at most 5,000 files and 500 MB, each file at most 64 MB (as when a folder is opened or a project comes from a forge), and a zip that expands suspiciously far is refused whole.

On the start page, a dropped folder opens as a project Desktop only, and a zip file (or, in the browser, a folder) becomes a new project, which you then save where you choose. To make a new project of a folder or a zip without dropping it, use Import a Project.

History and versions

Every project has a history, and on the desktop that history is a git repository in the project's folder, whether or not it is ever pushed anywhere.

Saving does not make a version each time: that would bury the history. A version (a commit) is made when something changed since the latest one:

  • after five minutes without typing;
  • when the project closes;
  • before something replaces the files: a restore, a pull, accepting all suggestions;
  • before every Sync;
  • on File › Save, and with Name This Version… (the tag button in the History section), which gives it a name of your own.

On the desktop, a folder that is not in a repository becomes one on its first save. A folder already in a repository of its own is used as it is: it gets the same versions, except that File › Save only saves there. In the browser, versions are kept in the browser, with the same comparisons and restores.

The versions TeXCraft makes by itself (after a pause, on closing, before a restore) do not pile up: while you work, each one takes the place of the one it made before, and says everything that changed since the version before that, as long as that one was made by TeXCraft while the project is open and has not been sent anywhere (pushed or synced). A version you make (File › Save, Name This Version…, a Sync, a push or a pull) takes in TeXCraft's own one before it and stays as it is; so does a version that was pushed, or one made outside TeXCraft (with git) or by another window. The next version after those is a new one.

The History section of the side panel lists the versions, newest first, each with what it changed, when, by whom and the files it changed. A version a save makes describes itself: the files added, edited, deleted or renamed and, for a LaTeX file, the sections whose text changed, as the outline names them, for example Edited Introduction and Results (main.tex); added figures/plot.png. When that would be longer than a line, it says less (the sections, then the folders, then only how many files), and hovering over the version lists each file. A version you name keeps your name. Choose one to see what it changed in each file, line by line (What this commit changes). From there:

  • Restore This File… brings one file back as it was;
  • Restore the Project at This Version… brings back every file, and removes the files added since.

Before a restore, the project as it is is kept in a version; the restored files are then saved like any change. Nothing is lost: the history keeps every version, including the one you restored over.

Commits carry your git identity when your system has one (git config user.name and user.email), and the name TeXCraft otherwise. When TeXCraft makes the repository, it also writes a .gitignore that keeps build files out.

To keep the history on GitLab, GitHub or another git server too, see Sync, Push and pull and Save Project to GitHub or GitLab.

The .texcraft folder

TeXCraft keeps a few things of a project in a hidden .texcraft folder inside it, so they travel with the project and its history:

  • .texcraft/review/: the comments and suggestions, one file per thread (Comments and suggestions);
  • .texcraft/words.txt: the project's own spellings;
  • whether AI may be used in this project (AI assistance).

Projects in the browser

The browser version keeps projects in your browser's storage for this site, by name. The start page lists them under Projects in this browser, to open or to delete. The page asks before you leave it with changes not kept yet (typing that has not paused, or a write that failed).

When you first save a project, TeXCraft asks the browser to keep the site's data for good. Under Projects in this browser the start page says what the browser answered, and how much room the projects take:

  • Kept until you delete them: the browser agreed; it does not remove the projects on its own.
  • The browser may remove them when space runs low: it did not (some browsers decide by how often you visit the site, or ask you). Keep a copy elsewhere, as below.

If the browser has no room left, the save fails and TeXCraft says so on the status line and beside the project's name (Not saved): the project keeps its unsaved changes, and leaving the page warns you. Download it as a zip, delete projects you no longer need, then save again.

File › Download Project as Zip Browser only downloads the project's files (and its review's comments, in .texcraft/review/) as one zip file. Dropped on the start page, it becomes a project again with the same files; on the desktop, unzip it and open the folder, comments included.

Projects stay in this browser on this computer only. Clearing the site's data in the browser deletes them. To keep a copy elsewhere, download it as a zip, or save the project to GitLab or GitHub (how); exports and the PDF can be downloaded at any time.
