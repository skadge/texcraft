Troubleshooting

What to do when a build fails, when the browser version lacks a package, and where to look when something else goes wrong.

Common build errors

Open the build log: each message says what went wrong in words, with help and a link to its line. The first error is usually the one to fix; later ones often follow from it. With a model connected, Explain gives a second opinion Desktop only.

Undefined control sequence
A command TeX does not know: a typo, or a command from a package the preamble does not load. Quick Fix (Ctrl+.) on the underlined command offers the \usepackage line when the engine knows which package defines it.
Missing $ inserted
Something that only works in a formula, such as _, ^ or \alpha, is outside one. Put it in $…$, or write \_ for a plain underscore.
File not found
An \input, \include or \includegraphics names a file that is not in the project, or not at that path. Paths are relative to the main document's folder, and their case matters.
Runaway argument, or a paragraph ended before something was complete
A brace { or an environment is not closed. The line the message points to is where TeX noticed, which can be after the place to fix.
"??" in place of a reference or citation
While a build is still running its passes, the draft PDF shows "??"; wait for the build to end. If they stay, the label or the citation key does not exist (the log says which), or the bibliography file is not named in \bibliography or \addbibresource.
A build that seems stuck, or results that make no sense
Use Stop Compiling, then Delete Build Files in the Compile button's menu, and compile again: the next build starts from scratch.

Packages

On the desktop, TeXCraft uses your TeX Live (2025 or 2026) when one is installed. A package your document needs and your TeX Live lacks is downloaded from TeX Live the first time; without any TeX Live, TeXCraft keeps a TeX tree of its own and fills it as documents need it. Either way the first build of a new package needs the network.

Packages in the browser Browser only

The browser version serves its own TeX tree: the common classes and packages, and those of every template. A document that needs a package outside it fails to build, and the log names the file it could not find.

  • If the package is a single file (a .sty or .cls), adding that file to the project usually works.
  • Otherwise, build the project in the desktop app, which downloads what it needs.

Not yet: downloading missing packages during the build in the browser.

The first build of each visit downloads the TeX files the project reads, which can take a few seconds; they are kept for the next visit.

Installing and starting

The AppImage does not start
It needs glibc 2.36 or newer (Debian 12, Ubuntu 24.04, Fedora 37 and later; not Ubuntu 22.04) and FUSE 3 (fusermount3). Without FUSE, run it with --appimage-extract-and-run. Make sure it is executable (chmod +x).
The Flatpak does not use my TeX Live
The sandbox cannot see it. The Flatpak keeps its own TeX tree inside its sandbox and downloads packages into it, so its first build needs the network. It can open projects in your home folder.
Windows or macOS refuses to open it
These builds are not signed yet. On Windows choose More info › Run anyway; on macOS, right-click the app and choose Open the first time.
"The preferences cannot be saved"
TeXCraft could not write its settings folder (below); changes are kept for this session only. Check that the folder exists and is yours.
A sign-in or the AI token is forgotten at each start
They are kept in your system's keychain (the Secret Service on Linux, the Keychain on macOS, the Credential Manager on Windows). Without a working keychain they last only while TeXCraft runs.

In the browser

  • My projects are gone: projects live in the browser's storage for the site; clearing the site's data, or using a private window, removes them. Save projects you care about to GitLab or GitHub.
  • Paste from the menu does not work: a web page can read the clipboard only with the keys; use Ctrl+V (Cmd+V on a Mac).
  • A dropped file is not added: some drops carry no file; the status line says so. File › Add to Project › Add Files… always works.

Logs and reporting a problem

The desktop app writes its warnings and errors to the terminal it was started from. For more detail, start it from a terminal with RUST_LOG=info (or debug):

RUST_LOG=info texcraft
RUST_LOG=info ./TeXCraft-*.AppImage
flatpak run --env=RUST_LOG=info io.gitlab.severin_lemaignan.TeXCraft

A build's own log is in the build log's Raw log, which you can copy or save. An internal error in a command is caught and shown as a message instead of closing the window.

Report problems on the issue tracker, with the version (Help › About TeXCraft), your system, what you did and what happened. Leave out private text and any token. A security problem goes through the project's private security reporting, never a public issue.
