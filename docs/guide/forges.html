GitLab and GitHub

TeXCraft works with projects kept on GitLab or GitHub, including your organisation's own GitLab server or GitHub Enterprise Server. It talks to them directly: there is no TeXCraft server in between.

There are two ways to work with a repository:

  • Import a project from GitLab or GitHub: on the desktop it is cloned into a folder, with its remote set; in the browser it opens from the service's web API, and your changes are committed back to its branch. Nothing to set up.
  • Push and pull a project folder that is a git repository with a remote, as git does. Desktop only

Either way, Sync beside the project's name does it all in one click.

Not yet tried widely: pushing, pulling and saving a project to a new repository are new in 0.12.0 and have had little use against the real services yet. Keep a copy of important work, and please report what goes wrong.

Signing in

TeXCraft needs your permission to read a project, and to commit to it. You can sign in, or give a personal access token.

Sign In with GitLab
In Import a Project and the Commit dialog, or in Settings › Accounts. GitLab's page opens in your browser; once you let TeXCraft in, it is signed in. It asks only to read at first; the first commit asks once more, with Allow Commits on GitLab. On the desktop the sign-in is kept in your system's keychain, so a restart stays signed in; in the browser it lasts as long as the tab is open.
Sign In with GitHub Desktop only
The dialog shows a code, with Copy Code and Open GitHub's Page; enter the code on GitHub's page. In the browser, GitHub's sign-in does not answer web pages, so use a token there.
A personal access token
Choose Use a personal access token instead in the dialog, and paste the token in the Personal access token field. With Remember on this computer (ticked at first), TeXCraft keeps the token in your system's keychain, so that the next import from the same service, Push, Pull and Sync need no token, after a restart too; in the browser, Remember in this tab keeps it in the tab's session storage until you close the tab. Untick it and the token is kept only while TeXCraft runs (in the browser, while the page is open). A token is never written to the preferences or a log. Settings › Accounts lists the tokens kept, with Replace… and Disconnect….
  • GitLab: the read_api scope to open a project, api to commit or make a repository.
  • GitHub: a fine-grained token with access to the repository, with Contents read-only to open it, read and write to commit, and Pull requests read and write to open a pull request; Administration read and write to make a repository. A classic token needs the repo scope.

Disconnect…, in Settings › Accounts, asks first, then forgets the sign-in. On GitLab it also withdraws TeXCraft's access; on GitHub, remove TeXCraft under your GitHub account's settings, in the applications you have authorised.

Importing a project from GitLab or GitHub

File › Import a Project… (also Import… on the start page), then the GitLab or GitHub card, asks for:

  • the Account: signed in, or a personal access token;
  • the Project: its web page or any page under it, its clone address, or just group/project. Once you are signed in, or the token is typed, the line under the field says Fetching your repositories… with a spinner while your list is fetched, then how many there are (142 repositories), or why it could not be had; until it has come, the suggestions say Still fetching…. Then the projects you can reach are suggested as you type. An address on the other service offers Switch to GitHub (or GitLab);
  • the Branch: a list of the project's branches, with the default branch chosen;
  • Into Desktop only: the folder the project is cloned into (see Importing a project).

On the desktop the project is cloned into its folder with its whole history, its remote set, so Sync, Push and Pull work at once. In the browser it opens through the service's web API and is kept with your browser's projects, with its link to its branch, so a reload keeps your changes and Commit sends them back.

For a project on your organisation's server, use the GitLab Server card: it lists the servers added, with Add a Server… (see below).

The top bar shows the project, the branch and how many files you changed. Hidden files (such as .gitignore) stay on the branch as they are. Files over 64 MB are skipped, and said, as when a folder is opened; a project over 200 MB is refused.

Importing from Overleaf Desktop only

Overleaf lets a project be cloned with git. In Import a Project, choose Overleaf, paste the project's Clone address (it starts with https://git.overleaf.com/; a whole git clone … line works too) and a Git token, made in your Overleaf account settings under git (your password does not work there). TeXCraft checks both, then clones the project. Sync then sends your versions to Overleaf and takes in what was changed there, with the same token. Overleaf refuses some things git allows, such as other branches; its message is shown as it says it. In the browser Overleaf's git server cannot be reached: download the project as a zip on Overleaf and import the zip.

Committing

File › Commit to GitLab… (or Commit to GitHub…) lists the files you changed and asks for a message. Before committing, TeXCraft looks at the branch: commits others made in the meantime are taken in first, so nothing anyone committed is written over.

Keeping up with the branch

File › Update from GitLab (or GitHub) takes in what others committed. TeXCraft also checks by itself every two minutes, and when its window comes back to the front, quietly: what came in is said on the status line.

  • A file changed only on the branch is taken in.
  • A text file changed on both sides is merged line by line, when the changes are on different lines.
  • Changes to the same lines, a file deleted on one side and changed on the other, and binary files changed on both sides are conflicts: nothing is taken in until you choose, for each file, Keep mine or Take theirs. The top bar shows how many files are in conflict, and the next commit offers the same choices.

Comments and suggestions (review) are committed and updated with the project.

A new branch and a merge request

When you cannot commit to the branch (it is protected, or your role does not allow it), or you prefer not to, the commit dialog offers Commit to a new branch and open a merge request (on GitHub, a pull request). Your changes go to the new branch, the request is opened into the original branch, and its link is shown. The project then follows the new branch, so later commits add to the same request.

Sync

When a project has a remote (its folder's git remote, or the branch it was opened from), ⇅ Sync stands beside its name in the top bar, with what waits to go either way: ↑2 for two versions to send, ↓1 for one to receive (as last seen); hovering says it in words. One click:

  1. makes a version of your changes, if there are some (History);
  2. takes in the remote's new commits, merging text files changed on both sides;
  3. sends your versions.

Changes made on both sides merge by themselves when they touch different words: two people editing different sentences of one paragraph, even on the same line, a citation added in one place and a typo fixed in another, a formula edited and the prose after it. The status line says what came in and what went out. When both sides changed the same words differently (or words right next to each other), nothing is taken in yet: a dialog lists the files, and for each you choose Keep mine or Take theirs, then Sync again. When the server wants a token TeXCraft does not have (or refuses the one it has), it asks for one, with Remember on this computer to keep it in the keychain for next time; a token kept already is used without asking. Sync is also in the File menu.

For a project opened from GitLab or GitHub, Sync commits your changes to its branch with a message that says what changed (or, with no changes, takes in the branch). Commit to GitLab… stays there to write your own message.

Projects on Overleaf Desktop only

A project cloned from Overleaf with git has a remote such as https://git@git.overleaf.com/…. TeXCraft recognises it and shows the service's name, with a small cloud icon, beside Sync and in the History section. Sync works as with any git remote. Overleaf asks for a git authentication token: make one in your Overleaf account's settings, and paste it when TeXCraft asks. A project imported with Import a Project already has it, kept in your keychain if you chose Remember on this computer.

Push and pull for project folders Desktop only

A project folder is a git repository (History). When it has a remote on GitLab, GitHub or another server, the History section shows it (the service's name when TeXCraft recognises it), with ↑ Push and ↓ Pull buttons and what waits to go either way (↑2 ↓1, in words on hover). They are also in All Commands (Ctrl+Shift+P).

Push
Makes a version of your changes, then sends the commits of the branch you are on. If the remote's branch has commits you do not have, the push is refused before anything is sent: pull first (or Sync). A refusal by the server (a protected branch, for example) is shown with its reason.
Pull
Makes a version of your changes, then takes in the remote's commits: a fast-forward when you have nothing new, or a merge when both sides have commits. Text files changed on both sides are merged where the changes touch different words (as Sync does); when they cannot be, the pull is refused, naming the files, and nothing changes (Sync offers the choice of a side for each). A file changed on disk outside TeXCraft and not committed stops the pull too.

TeXCraft uses your sign-in or token for the remote's server, and asks for a token when it has none. It speaks git over HTTPS; an SSH address (git@gitlab.com:group/project.git) is reached over HTTPS at the same path.

Not yet: SSH itself, other branches than the one checked out, force pushes, and merging the two sides of a conflict inside a file (keep one side, or merge it with git). For those, use git alongside TeXCraft: the repository is an ordinary one.

Save Project to GitHub or GitLab

A project that is on no server yet can get a repository of its own: File › Save Project to GitLab or GitHub › Save Project to GitHub… or Save Project to GitLab… (also in the History section while the folder has no remote). The dialog asks for the server, the owner (you, or one of your organisations or groups), the name (suggested from the folder's), who can see it (Private, the default, or Public) and an optional description.

  • On the desktop, TeXCraft makes the repository, sets it as the folder's origin, and pushes the whole history. Unsaved changes are saved and committed first.
  • In the browser, the files go in as the repository's first commit (the versions kept in the browser stay there), and the project is then linked to it as if opened from it.

The dialog ends with Open in Browser for the repository's page.

Linking a project to a repository that exists

To keep a project you already have in a repository that already exists (one made on GitLab or GitHub with a README, a copy on your organisation's server, an Overleaf project's git address), use File › Link to a Repository…, also in the History section and in All Commands (where Add a Remote finds it too). Its cards are Import's: GitLab, GitHub, Overleaf, a GitLab server or any git address, your default connection first. Choose the repository and its branch as for importing; the project stays where it is.

Before anything changes, What happens says what linking will do, checked on the server:

  • The repository is empty: your project's history is sent to it.
  • The repository has versions of its own: they are merged with your project's. Files only on one side are kept; for a file both have with other contents, you choose Keep mine or Take theirs there, before Link.
  • The repository has this project's history already: Sync brings the two up to date.

If the project has a remote called origin already, the dialog asks a name for this one; Sync then uses the new repository, and origin stays. Linking makes a version of your changes first and never forces a push, so nothing of either side is lost; the merge is in the history like any other version. After linking, Sync works with the repository at once.

In the browser, GitLab and GitHub are linked through their web APIs (the repository's files come into the project, and Sync sends yours); other git servers do not answer web pages, so Overleaf and git addresses are linked from the desktop app. GitHub's web API cannot write into an empty repository: add a README there first.

To stop syncing with a repository, Unlink… in the History section asks first, then removes the link: neither the project nor the repository changes.

Your organisation's servers

A company's or a university's GitLab, or a GitHub Enterprise Server, works as gitlab.com and github.com do, once TeXCraft is registered on it as an application, by you for yourself or by its administrator for everyone.

  1. In Settings › Accounts, choose Add a Connection…, then GitLab Server or GitHub Enterprise Server, and type the server's address (any page on it will do). The Open dialog offers the same for a project on a server it does not know.
  2. TeXCraft checks that the server answers as GitLab or GitHub does, then shows what to register on it, each value with a Copy button, and a button opening the right page.
  3. Paste the Application ID (on GitHub, the Client ID) you get, and choose Add Server. Then sign in with its own Sign In button.

A link can propose a server too: https://texcraft-893d51.gitlab.io/?gitlab=https://git.example.org/group/project&client_id=…, in the browser, or the same address given to the desktop app when starting it. TeXCraft always asks before adding it.

In the browser, the server must accept requests from web pages; many do not. TeXCraft says so when it gets no answer, and the desktop app is then the way.

On the desktop, servers whose certificates come from your organisation's own certificate authority work when that authority is installed on the computer.

Servers provided by your organisation Desktop only

An administrator can give everyone the servers, ready to sign in to, with a file named texcraft-forges.toml. TeXCraft reads it at start from the system-wide folder, then from your settings folder (where); the first file to list a server wins.

The system-wide folder
SystemFolder
Linux and other Unix systems/etc/texcraft/
macOS/Library/Application Support/TeXCraft/
Windows%ProgramData%\TeXCraft\
 
[[server]]
address = "https://git.example.org"
service = "gitlab"     # or "github" for a GitHub Enterprise Server; gitlab when left out
client_id = "…"        # the application registered for everyone

These servers show as "Provided by your organisation." in Settings › Accounts and cannot be removed there. An entry TeXCraft cannot use is left out, and Settings › Accounts says why.
