- 2026-11-25: F4 (docs/ROADMAP.md): tables and figures in the formatted view. `texcraft_latex::table` reads a `tabular` as a grid: its column specification (`l c r`, `p{…}`/`m{…}`/`b{…}` and `|`), rows split on `\\` (with its `*` and `[…]`) and `\tabularnewline`, cells on `&`, both at the body's top level so a group or an argument stays in its cell, `\multicolumn` spans, and `\hline`, `\toprule`, `\midrule`, `\bottomrule`, `\cline` and `\cmidrule` between rows; what it cannot show faithfully it names (`\multirow`, a table or another environment in a cell, `@{…}`, `!{…}`, `>{…}`, `<{…}`, `*{…}` and unknown column types, a rule inside a row, text beside a `\multicolumn`, more cells than columns, `\noalign` and kin, a table not closed), and such a table stays as its source with the reason in its header and accessible name. Its edits change only what they must: a cell's text; a row above or below (a row under a header's rule goes under the rule; a last row without `\\` gets one); a row deleted with its line; a column left or right, or deleted, in the specification (with its `|` where the table has them) and every row, a `\multicolumn` across it growing or shrinking by its count; a column's alignment by its letter alone; borders none, all (`|` everywhere and `\hline` between all rows, rows inserted and deleted keeping one rule each) or booktabs (`\toprule`, `\midrule` under the first row, `\bottomrule`, partial rules renamed between `\cline` and `\cmidrule`), each rule renamed, added on a line of its own or removed with its line. booktabs is never added to the preamble: the edit returns the package and the window says when the main document does not load it. The view shows a `tabular`, alone or in a `table` float holding it with `\centering`, a caption and a label, as a grid: columns as wide as their widest cell (scaled to the measure), each cell's text set by its column's alignment (or its `\multicolumn`'s) and edited in place as a line of the view's text (typing escaped, so `&` is `\&`), the table's own rules and bars drawn, faint lines for every cell while the caret is in it, and the caption with its label above or below as in the source. While the caret is in a table a floating toolbar over it offers Row above, Row below, Delete row, Column left, Column right, Delete column, the column's alignment and the borders, each a `table.edit` command. Keys: Tab and Shift+Tab select the next and previous cell's text, Up and Down go to the cell above and below (and out of the table from its first or last row), Escape goes to the toolbar and Escape there back to the cell; dragging a selection now tells side-by-side cells apart. Figure cards have an Edit Figure… button opening a dialog: the image (from the project's images, written as LaTeX finds them from the main document), its width as a share of the line (a width in other units is kept unless the slider moves), where LaTeX may place it (here, top, bottom, a page of floats; `!` and `H` kept), the caption as LaTeX source and the label; Apply runs `figure.edit` with the parts that changed, each changing only its own source or added on a line of its own. Commands for agents: `table.inspect {path, at?}` (each table's columns, rows of cells with their text and span, borders, or why it stays as source), `table.edit {path, at, op, row?, column?, text?, latex?, align?, borders?}`, `figure.edit {path, at, image?, width?, placement?, caption?, label?}`, `figure.insert {path, at, image, …}` (a new figure on lines of its own, a project image written from the main document's folder). - 2026-11-25: C5, step 2 (docs/forges.md): keeping up with a GitLab branch. `texcraft_forge::merge::merge3` is a three-way merge of text files line by line (diff3 over the `similar` crate's Myers diff): changes to different lines merge, the same change on both sides is no conflict, overlapping or neighbouring changes and binary files are conflicts, and the merged file keeps the local line endings. `forge.pull {token?, resolve?, background?}` takes in the branch's new commits: files changed only there are taken, files changed on both sides merged; a conflict (overlap, deleted on one side and changed on the other, added twice, binary) takes in nothing and is listed by `forge.status` until settled with `resolve: {path: "mine" | "theirs"}` on a pull or a commit. `forge.commit` catches up the same way before committing on top of the head, and with `new_branch` commits the changes from the base to a new branch (`start_sha`) and opens a merge request (`POST …/merge_requests`), the project then following the new branch; a protected branch or a role that cannot push refuses the commit with nothing sent and offers that way (`cannot_push`). Updates computed while the user kept editing are merged into the edits, or the edits are kept and said. Review threads (`.texcraft/review/*` only) are loaded from the branch into the review, committed and pulled with the project. Interface: File › Update from GitLab; the commit dialog lists files in conflict with Keep mine and Take theirs for each and a "Commit to a new branch and open a merge request" option (the only one for a protected branch), reopens with its message after a refusal, and the merge request's link is shown once opened; the top bar shows files in conflict; the branch is checked quietly every two minutes and when the window gets the focus back, while signed in. Tests against the fake GitLab (now with protected branches, `start_sha` and merge requests): pulls with and without conflicts, both resolutions, the merge request path, review threads round trip, and the merge's unit tests; the window's tests cover the conflict and merge request dialogs and the check on focus. Limits: no OAuth yet (step 3), no conflict markers or hand merge in the editor, choices per file.
- 2026-11-25: C5, step 1 (docs/forges.md): projects from GitLab with a personal access token. `texcraft-forge` is GitLab's REST API as plain async Rust over a transport (ureq on the desktop, on its own thread; `fetch` in the browser; an in-memory GitLab in tests): a project's address in any form users paste (HTTPS only, but for `localhost`), the default branch, the branch's head, the recursive tree page after page (`Link` or `X-Next-Page`), the files' blobs eight at a time checked against their git blob ids, changes found by blob id (a rename is a move), one commit with `create`/`update`/`delete`/`move` actions, and errors in words (401, 403 with the scopes needed, 404, 429 with `Retry-After`). Files over 10 MB are skipped and said, projects over 200 MB refused; hidden files, symbolic links and submodules stay on the branch. Commands: `forge.open {url, token, ref?, background?}` (the desktop opens the project in memory, linked to its branch and in no folder; the browser keeps it in the library with its link), `forge.status` (base, branch, changed files), `forge.commit {message, token?, background?}`: a protected branch is refused before anything is sent; a branch that moved since the base is compared with it, and its commits to other files are kept and taken into the project, while commits to the same files refuse the commit, naming them (the three-way merge is step 2); a commit someone made meanwhile is found by the new commit's parent and taken in. With `background` the commands return at once and `Session::poll_forge` gives the outcome. Tokens are kept for the session only, per instance, never in the library, preferences, logs or results. Interface: Open from GitLab… on the start page and in File (address, branch, token with its scopes explained and a note that it is not kept), the project and branch with the number of changed files in the top bar, File › Commit to GitLab… (the changed files, a message, the token again when the session has none), outcomes on the status line. Limits: the token is asked again after a restart or reload; review threads are not carried to or from the branch; files are fetched one blob each (no archive); on the desktop the link lasts while TeXCraft runs (Save Project As copies the project into a folder, which opens unlinked later).
- 2026-11-25: E9: folding and several carets. `texcraft_latex::fold::regions` finds what folds: environments spanning lines (math and verbatim ones too; not `document`), sections up to the next heading of the same or a higher level or `\end{document}` (trailing blank lines left out), and the preamble from `\documentclass` to before `\begin{document}`; one region per first line, the widest. The editor's gutter has a fold marker on each region's first line (shown when folded, on the caret line, or with the pointer over the gutter); a folded region keeps its first line with a "…" chip and its other lines take no room, while line numbers keep counting them. Both the marker and the chip are buttons named "Fold lines 12–40, section Introduction" (or Unfold), the marker with its expanded state; a fold or unfold is said on the status line, which is announced. Folds are kept per open file as buffer marks on their first line, so they follow edits; a fold unfolds when its region is gone (its structure broke) and when the caret lands inside (Go to Line, search, a diagnostic, a jump from the PDF or the outline, a motion). Left and Right step over a fold, Up and Down skip it. Commands: Edit › Fold (`edit.fold`, Cmd+Shift+[), Unfold (`edit.unfold`, Cmd+Shift+]), Fold All (`edit.fold_all`, Cmd+Alt+Shift+[), Unfold All (`edit.unfold_all`, Cmd+Alt+Shift+]); in Vim `zc`, `zo`, `za`, `zM`, `zR`, and `j`/`k` step over a fold rather than open it. Several carets, outside Vim mode: Alt+click adds a caret (or takes one away; Ctrl+click stays Go to Definition), Cmd+D selects the word at the caret, then adds each next occurrence; typing, Backspace, Delete, Enter, Tab, the arrows, Home and End act at every caret, each edit at all of them one undo step; Copy and Cut take every selection, one per line; Escape returns to one caret; the number of carets is announced. Limits: other commands (Comment, Tab with a selection over lines, completion, closing brackets) act on the primary caret only; a run of typing at several carets is undone a character at a time; Vim's `dd` on a folded line deletes only that line (the fold then opens); folds are not kept across sessions.
- 2026-11-25: C8, the browser: projects of the browser's library keep a history too. Each save that changes a project records a version ("Saved with TeXCraft", by the review name, else TeXCraft); a save that changes nothing records none. `texcraft_history::store` keeps the versions as values: each file's bytes once, under its git blob id (SHA-1 of `blob <length>\0<bytes>`, through `gix-hash`, which also builds for wasm32), each version its parent, time, author, message and files (paths and blob ids), its id the SHA-1 of that manifest. The library keeps a project's history with it (`Stored::history`); a save tells the shell only what is new (`Change::Versions`: the version and the bytes the history did not have), a rename moves the whole history and a delete removes it. The web shell keeps versions and bytes in their own IndexedDB stores (`versions`, `blobs`, by `<project>/<id>`; database version 3, older databases open with empty histories) and loads them at start. `history.status/list/show/diff/restore` read it as on the desktop, so the History panel works unchanged; `history.commit` is refused there (saving already makes the versions). Limits: versions are not git commits yet (no tree or commit objects; the blob ids are git's, so C5 can write them); the whole history is loaded into memory at start, and nothing is ever pruned.
- 2026-11-25: C3 (R2 of docs/collaboration-roadmap.md): suggested changes. A suggestion is a review thread with a `suggestion` (`texcraft-review`: author, time, `replacement`, `outdated`): its anchor is the passage it replaces (empty for an insertion), and it follows edits as a comment's anchor does; an edit inside the passage makes it outdated (rejectable, never applied). Kept as files of kind `suggestion` in `.texcraft/review/` (docs/review-format.md) or in the browser's library, like comments. Commands: `review.suggest {path, start, end, text, id?}` (with `id`, changes one's own), `review.accept`, `review.reject`, `review.accept_all {path?, author?}`, `review.reject_all`, `review.list {kind}`; accepting is one edit with the review origin, Accept All one per file, and the first of overlapping suggestions is taken while the others are reported outdated. An undo of an accept (an edit of origin `undo` that puts the passage back) reopens the suggestion, a redo accepts it again. Suggest mode (the toolbar's Suggest switch, Edit › Suggest Changes, Cmd+Shift+E, `:set suggest` in Vim) shows the file with its suggestions in it, each passage struck through and its replacement underlined in the author's colour, and reads edits of that text as suggestions (`texcraft_review::view`): typing on extends one's own, deleting marks text and moves the caret past it, an edit inside someone else's is refused with a message. Cards in the margin and the Review panel say the change in words ("Replace “colour” with “color”") and as struck and underlined text, with Accept, Reject, replies, Withdraw, and an outdated note; Accept All and Reject All act on the file shown. Builds ignore suggestions; `build.suggestions {on}` ("Show suggestions in the PDF", in Suggest mode's line and the Review panel) builds with them applied without writing them, and the line says which text the PDF shows. Limits: outside Suggest mode a replacement is only in its card (the passage is struck through, an insertion point marked); an accept made in Suggest mode is not in the editor's undo history; in Suggest mode completion, hover and go to definition are off and diagnostics keep the file's places; suggestions outdated by an accept stay outdated when it is undone; an insertion is found again on load by its offset only (context matching comes with R4); with suggestions in the PDF, SyncTeX's lines are those of the text with them.
- 2026-11-25: O2, O3: a build makes one of three kinds of PDF (`build.options` `output`; Settings › Building › PDF for, and the Compile button's menu; kept in the preferences): for the screen (the default), accessible, or for print. An accessible build is retex's `accessible(true)` (`--accessible` in the browser): a tagged PDF that declares PDF/UA in its XMP, checked for what screen readers need. A print build also writes a PDF/X beside the PDF (`Retex::pdfx`, `-output-format=pdf,pdf-x4` in the browser), PDF/X-4 or PDF/X-1a (`pdfx`), with a bleed (`bleed_mm`, 3 mm by default, up to 20) and crop marks (`crop_marks`, on by default); the preview keeps showing the PDF as designed, so SyncTeX and the print checks' places match it, and Save PDF / Export › PDF write the PDF/X (`kind` in their result; a print build that wrote no PDF/X saves nothing and says why). The build log has an Accessibility filter (findings of origin `accessibility`) and a Print filter (`print` and `PDF/X` messages), shown for a build of that kind or one with such findings, each message linking to its source line; a print message whose check retex placed on the page also links to that page ("Page 2"), which shows the PDF with the area marked. A print build's log starts with "Ready for print" or "N problems" (warnings and errors of the print checks and the PDF/X, and a missing PDF/X). `Outcome` keeps the kind of PDF and a print build's `Preflight` (the PDF/X, its print checks with their page area and source place, the standard's rules); agents get `output`, `accessibility` and `print` (`ready`, `problems`, `checks`, `rules`, `pdfxBytes`) in `build.result`. retex 2.5.0's worker takes the PDF/X options but not `accessible`, so on the desktop an accessible build runs in process (without the worker's preamble snapshot); and retex rewrites LaTeX's tagging messages (an image without alternative text, formulas without MathML, the PDF's language, a class without tagging) with no origin, so TeXCraft gives those the origin `accessibility` itself (docs/retex-changes.md, R18 and R19).

- 2026-11-25: F2: the formatted view draws formulas typeset by retex after the main document's preamble, on the desktop. `texcraft_compile::formulas` sends the formulas it has not typeset yet in one batch of retex fragments (one page each, as tight as its box) on a thread of its own, through a `retex worker` process of its own (a batch in the build's worker would stop a running build), or in process where there is no worker program (the CLI, tests); it keeps each by preamble, source and mode, so editing one formula typesets that one only. `Session::formulas` finds a file's formulas in its view model (display environments become one `aligned` or `gathered` formula without `\label`, `\tag` and `\nonumber`) and takes the body size from the class options.
