- 2026-11-26: Browser fixes from testing 0.14.0 (issues #16, #20, #24, #26). **First builds (#16, W9):** a first build in the browser stopped once per package folder it had not fetched (after the first second and a half the worker can no longer fetch synchronously, so the run stops, fetches the file and its folder, and starts again from the start, reading every file again: the example project, with tikz, stopped about 26 times, and the status showed the same "reading natbib.sty" over and over). `cargo xtask tree-site` now also writes, for each class and package of `tree.txt`, what a document loading it reads beyond the blank project (`seed/reads/class/NAME.txt`, `seed/reads/package/NAME.txt`, from the `-recorder` runs it already made); before a build, the worker reads the project's `\documentclass`, `\usepackage`, `\RequirePackage` and `\bibliographystyle` lines (`texcraft_compile::prefetch::loads`), fetches those lists and the files they name together (a package without a list: its file, and what that file loads), and a run that stops for a package's file fetches what that package reads with it. While a run started again reads what the last one read, its progress lines are not passed on (`prefetch::Reported`); the status says "Downloading LaTeX packages: 12 of 34 files…" (a new `Event::Fetching`, `Progress::fetching`), then "Reading the downloaded LaTeX packages…" until the build reads something new. **PDF/X (#20):** an ordinary build asks for no PDF/X (the default kind of PDF is Screen; a PDF/X is made only for "PDF for: Print", which the browser keeps in its preferences, or for a document that claims to be one, as retex does); the browser's tree lacked TeX Live's colorprofiles (FOGRA39L_coated.icc, sRGB.icc), so a print build failed there: `tree.txt` now takes `tex/generic/colorprofiles`. **Touch (#26, A12):** a finger's drag scrolls the source, the formatted view, the PDF and the file list instead of selecting or moving files (`touch.rs`); a tap places the caret, a long press selects the word (a glyph in the PDF) and moving the finger, still down, extends the selection; a mouse selects as before. **Typing in the formatted view (#24, F3):** egui gives up a widget's focus when a click lands on another widget, and the view's text takes the keyboard on one widget while its lines take the pointer, so a mouse click focused the text as the button went down and gave the focus up as it came up (the caret showed, then went away, and typed or composed text went nowhere); a click on a line now keeps the focus there. The earlier tests gave the text the keyboard through assistive technology, never with a click. Tests: a mouse click then `Text` and IME events reach the formatted view (kittest, fails before); `prefetch::loads` on a document with comments and lists, `Reported` over a restarted run (compile); touch drags and long presses in the source and formatted view (kittest). To check in a browser: a first build of the example project (a few stops at most, the status), a print build; on a phone, scrolling and long-press selection.
