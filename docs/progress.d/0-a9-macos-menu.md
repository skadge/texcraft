- A9 (docs/ROADMAP.md), the macOS menu bar: built, not tried on a Mac. The menus are put in the system's menu bar through craft-libs' `craft-menu` (at the pinned rev): `App::menu_tree` (crates/ui-egui/src/system_menu.rs) builds File, Edit, Insert and Help from the engine registry and the view commands exactly as the in-window bar draws them (same order, groups, translated labels, Open Recent with Clear Recent Projects), each entry with its command id, its shortcut from the keymap (the user's changes included) and whether it can run now; About and Settings are tagged for the app menu, and Quit is craft-menu's, which asks the window to close so unsaved changes are asked about first. `App::system_menu_layout` lays it out for the Mac (app menu, File, Edit, Insert, Window, Help). The desktop shell, on macOS only (apps/texcraft/src/mac_menu.rs), installs it with `craft_menu::mac::install` in eframe's creator and hands the driver to `App::set_system_menu`; `raw_input_hook` feeds the menu's key equivalents back to egui as key presses, so the keymap runs them as before. Each frame the app sets the gate (a dialog, the gallery or a presentation greys the menus and drops their clicks; recording a shortcut; a text field with the keys), runs the chosen entries through `ui_cmd::run_with` (an Open Recent entry is `project.open` with its `path`), and syncs the layout after drawing. With the system's menus the in-window menu bar is hidden, and `view.menu_bar` (F10) is disabled with the reason (Control+F2 reaches the system's menu bar). Everything but the AppKit install is platform-free and runs on Linux; `craft-menu` adds muda only on macOS. Tests (kittest, a stand-in backend): the tree has every in-window entry with its shortcut and enabled state, About and Settings land in the app menu, the in-window bar is hidden and a choice runs its command, a choice behind a dialog does nothing, Open Recent opens that project.
