- 2026-11-25: C5, self-managed servers (docs/forges.md, step 4): signing in to a company's or university's GitLab, or a GitHub Enterprise Server, as to gitlab.com. Settings › Accounts › Add a GitLab Server… (or Add a GitHub Enterprise Server…; the Open dialog offers it for a host with no application) asks for the address, checks it (`forge.check_server`: GitLab's `/api/v4/version`, its version or a 401 with GitLab's JSON; GHES's `/api/v3/meta`; in the browser, no answer is said as a server that does not answer web pages, with the desktop app as the way out), then shows what to register with Copy buttons (where, the name TeXCraft, the redirect URIs — the desktop's loopback and in the browser the page's origin — Confidential off, the scopes `api read_api read_user`; on GitHub the device flow), takes the Application ID and adds the server (`forge.add_server`, `forge.remove_server`). The server ({instance, service, client id}) is kept in the preferences, its sign-in in the keychain per host; a grant remembers its application, so renewal and revocation use the same one. GHES uses the device flow on its own host. A link `?gitlab=<address>&client_id=<id>` (the web page's query, or the desktop's argument) proposes a server and asks before adding it, then opens the link's project; an organisation's `texcraft-forges.toml` (system-wide folder, then the preferences' folder) lists servers shown as provided by the organisation, which cannot be removed or changed. The desktop's HTTPS for forges trusts the system's certificate store beside the bundled roots (rustls-native-certs, webpki-root-certs, both already in the tree).
